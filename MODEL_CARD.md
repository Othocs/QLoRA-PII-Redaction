# Model card: M5, a PII span detector (QLoRA adapter for Qwen3-1.7B)

M5 is the detector behind the PII redaction gateway in this repository. It is a LoRA adapter on Qwen3-1.7B that lists every piece of personal data in English customer-support text. Code aligns the listed values back to exact character spans, and the gateway then masks, pseudonymises, hashes or keeps them according to a policy.

The adapter is kept in a private Hugging Face repo and is not publicly released. It powers the [hosted demo](https://huggingface.co/spaces/Othocs/pii-gateway-demo) through a RunPod Serverless endpoint ([`docs/DEMO.md`](docs/DEMO.md)). This card documents the model as evaluated.

## Model

| | |
| --- | --- |
| Base model | [Qwen/Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B) (Apache-2.0) |
| Adapter | LoRA, r = 16, α = 32, dropout 0, on all 7 linear projections (q, k, v, o, gate, up, down); 17.4M trainable parameters (1.0% of 1.74B); about 45 MB |
| Training | QLoRA (4-bit NF4 base, bf16 compute) with TRL `SFTTrainer`; loss on the answer only. Learning rate 4e-4, cosine schedule with 3% warmup, 1 epoch, effective batch 16, max length 1,536 tokens |
| Data | `train_mix_32k`: 32,000 examples (below) |
| Compute | One NVIDIA A40: 137 min, $1.12 per run, 4.5 GB peak VRAM |
| Seeds evaluated | 13 (the reference adapter), 42 and 3407 |
| Configuration | [`configs/train/hpo/m4_base.yaml`](configs/train/hpo/m4_base.yaml), with `train_file=data/processed/train_mix_32k.jsonl` and `learning_rate=4e-4` |

The learning rate and rank were chosen in a three-phase search ([`docs/REPORT.md`](docs/REPORT.md) §5). Learning rate barely affected transfer, and r = 32 was no better than r = 16.

## Input and output

- **Input:** English text, split into windows of at most 1,200 characters with 150 characters of overlap.
- **Output:** JSON `[{"label": ..., "text": ...}]`, constrained by a JSON schema at decoding time (vLLM structured outputs), so every output parses.
- **Alignment:** values are aligned to the source left to right, with a fuzzy fallback for spacing and punctuation. Values that cannot be found in the text are dropped and counted as invented.
- **Labels (19):** GIVENNAME, SURNAME, TITLE, AGE, SEX, GENDER, DATE, EMAIL, TELEPHONENUM, STREET, BUILDINGNUM, CITY, ZIPCODE, IDCARDNUM, PASSPORTNUM, DRIVERLICENSENUM, SOCIALNUM, TAXNUM, CREDITCARDNUMBER.
- **Validators instead of the model:** IBAN and IP addresses are left to the gateway's deterministic validators.

## Evaluation

Character leakage is the share of gold PII characters left unmasked; lower is better. Results are seed-averaged over 3 seeds, with 95% CIs from 1,000 document resamples. Each test set was scored once per system. Full tables: [`results/phase4/phase4.md`](results/phase4/phase4.md) and [`results/phase4/final_coverage.md`](results/phase4/final_coverage.md); the protocol is in [`docs/EVALUATION.md`](docs/EVALUATION.md).

**Over-redaction** (share of masked characters that are not PII) is low for M5:

| Test set | M5 | Baselines |
| --- | ---: | ---: |
| Support desk | 5.8% | 16–23% |
| Held-out region | 0.6% | 1.4–19% |

On ABCD every system over-redacts 32–60%, because ABCD leaves order IDs and purchase dates unlabelled. M5's over-redaction there comes mostly from masking dates.

**Live gateway** (M5 + validators, one A40, single requests): median 0.38 s and p95 1.08 s per support message.

## Intended use

M5 is the detection step of a self-hosted redaction gateway. It runs on-premises, in front of logging, analytics or an external LLM, on English customer-support text and similar short business text. Use it together with the gateway's validators and policies, not as a standalone guarantee.

## Limitations

- **Real conversations.** On ABCD's human-typed chats, GLiNER-PII and OpenMed leak less than M5 (+2.3 and +1.8 pt, CIs excluding 0). The advantage M5 shows on LLM-written support text does not transfer to real chat transcripts. The most likely cause is that its training data contains no human conversational text.
- **Seed variance.** On small conversational sets, single seeds differ by about 1.5 pt (ABCD: 3.0, 1.5 and 3.1%; support desk: 0.7, 2.2 and 2.2%).
- **Invented values.** On Gretel-style documents, a large share of the values M5 returns do not occur in the text (repetition loops). They are dropped at alignment, which keeps them from causing false redactions but wastes tokens. On support text this is negligible.
- **Dates.** M5 tends to mask non-personal dates (order and purchase dates), which raises over-redaction.
- **Language.** English only, by scope. Cross-lingual results from earlier models are in the report, but M5 was not tuned for other languages.
- **Evaluation data.** The support-desk test sets were drafted by an LLM and not human-checked. TAB has only 127 documents. ABCD's labels come from fictional customer cards, with only 10 distinct names.
- **Latency.** M5 needs a GPU for interactive use: about 0.4 to 1 s per message on an A40, against well under a second on CPU for encoder models.

## Out of scope

- Medical records or protected health information. M5 was not trained or evaluated for clinical de-identification.
- Sensitive categories such as religion, health or sexual orientation, which are not among the 19 labels.
- Legal guarantees. No detector finds all personal data; the gateway's policies, audit logs and human review remain necessary.

## Reproducing

Training and vLLM evaluation run on a rented GPU through [`scripts/pod_sweep.sh`](scripts/pod_sweep.sh), with run lists in [`configs/sweeps/`](configs/sweeps/). The steps are in [`docs/REPORT.md`](docs/REPORT.md), appendix. The whole project cost about $21 in GPU time.
